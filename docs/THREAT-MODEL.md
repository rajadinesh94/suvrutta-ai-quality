# Threat model and boundaries

The reference serves fictional data from process memory over localhost. Its user selector is a demo fixture, not authentication. A malicious client can claim either fixture ID; therefore it must never be deployed as a real multi-user service or wired to private data. There are no secrets, external model calls, vault contents, or outbound endpoints. The server limits request body size, bounds text length, rejects unknown tools, and applies fixture consent and ownership rules inside the engine. Prompt-like text is inert input. These guards are examples of checks to test, not a replacement for product authentication and authorization.

Key threats for a real adapter: client actor spoofing, indirect prompt injection in retrieved stories, data exfiltration through tools, consent race/revocation after retrieval, cross-account source leaks, duplicate writes after timeouts, unsupported factual claims, decrypted plaintext reaching an unapproved provider, and private data in reports/traces/screenshots. Product integration must derive identity from verified server credentials, recheck authorization at every retrieval and action, use stable request IDs with durable receipts, and keep model/tool authority separate. Vault plaintext must remain within the approved design; this repo makes no claim about that design.

Reporting policy: synthetic local runs are ignored; inspect any screenshot or trace before export. Do not commit real stories, tokens, secrets, private URLs, product prompts, or identifying screenshots. Review the entire repository and history before sharing. Publication includes only a reviewed source snapshot; local history and raw artifacts are excluded. No operational security review or penetration test has occurred.
